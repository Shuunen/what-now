# Design: Voice Coach Companion for What Now

Generated by /office-hours on 2026-08-06
Branch: master
Repo: Shuunen/what-now
Status: APPROVED
Mode: Builder

## Problem Statement

What Now shows recurring tasks but is entirely screen/click driven. The user wants a personal AI coach that reviews today's remaining tasks, talks to them via voice to motivate them onto one task at a time, and lets them respond by voice ("done", "delay to tomorrow", "give me another task", "snooze — I'm busy elsewhere"). When a task is missing an attribute — most notably `reason`, but any attribute — the coach asks a clarifying question out loud ("what's the purpose of that task?") and writes the answer back. The goal is to finish daily tasks hands-free, without touching mouse or keyboard, using only free/local voice tech (no paid STT/TTS APIs).

## What Makes This Cool

A companion that sits in a tab while you work and nudges you through your day out loud, like having a low-key accountability coach who already knows your task list — not a chatbot you have to type at, and not a generic voice assistant that knows nothing about _why_ you set a task in the first place.

## Constraints

- No paid STT/TTS APIs — free/local only.
- "Nice human voice" required, not robotic OS TTS.
- Full voice loop (STT in, TTS out) from day one — not a text-first fallback.
- Continuous, always-listening interaction (no push-to-talk button) — explicitly chosen by the user despite the false-trigger risk this carries (phone calls, room conversation).
- Lives in a `/coach` subdirectory inside the `what-now` repo (resolved during /plan-eng-review — see Architecture Decisions). This is a deliberate deviation from the original "standalone, separate codebase" framing below: same repo means same CI, same `pnpm check`, same PR surface as the core app. The isolation goal is now a discipline (don't couple `/coach` code to core app internals) rather than a structural guarantee.
- **Revised during /plan-eng-review (Pipecat pivot):** the audio/voice pipeline is built on [Pipecat](https://github.com/pipecat-ai/pipecat), an open-source voice-agent framework, rather than hand-rolled in-browser JS. This means `/coach` is no longer a pure browser-only page — it pairs a small local Python server process (running Pipecat) with a browser client, alongside the already-required local Ollama service. See Architecture Decisions for what Pipecat replaces and why.
- Scoped to a dedicated view/tab that must stay open — no requirement to survive backgrounding or tab switches.

## Premises

1. Full voice loop (STT+TTS) is the point, not a text fallback — hands-free is core to the ask, agreed by user.
2. The coach does not need to survive backgrounding — a dedicated view/tab that must stay open is acceptable (browsers throttle/kill mic+audio in background tabs anyway, and PWAs can't reliably run continuous background voice loops).
3. **Revised (Pipecat pivot):** a locally-run Ollama model does the reasoning: task selection, spoken-intent interpretation ("done"/"delay"/"another"/"snooze"), dialogue generation, and deciding which missing task attribute to ask about next — accessed through Pipecat's `OLLamaLLMService`, an OpenAI-compatible interface to local Ollama, no API key required. Since Pipecat's server process talks to Ollama directly (both local processes on the same machine), the original CORS/`OLLAMA_ORIGINS`/browser-origin concern no longer applies — that was only a problem for a browser page calling `localhost:11434` directly, which this architecture no longer does.
4. **Revised (Pipecat pivot):** STT runs via a **local** Whisper-based service (e.g. faster-whisper) wired into Pipecat, not Chrome's cloud-touching Web Speech API. This fully resolves the privacy compromise the original design accepted — no microphone audio leaves the machine at all, actually matching What Now's "never leaves your browser" spirit rather than stretching its existing conditional exception. It also removes the Chrome-only browser constraint (Firefox/Edge were previously ruled out due to Web Speech API gaps) and the "restart-on-onend to survive Chrome's silence auto-stop" problem — Pipecat's pipeline handles STT session lifecycle.
5. **Revised (Pipecat pivot):** TTS runs via Pipecat's TTS service layer, most likely Kokoro (rated most natural-sounding among local options) or Piper (Pipecat has native support, though Piper was archived/read-only as of October 2025 — Kokoro is the actively-maintained choice and is preferred unless a concrete reason favors Piper). Runs as part of the local Pipecat server process rather than in-browser WebGPU/WASM.
6. Continuous always-on listening is accepted with its false-trigger risk (background phone calls, conversations in the room being misheard as commands) — the user chose this over push-to-talk knowingly.
7. "Delay to tomorrow" and "snooze" have no backing field in the current `Task` schema (checked `src/schemas/task.ts` and `convex/schema.ts`: only `completedOn`, `once`, `isDone`, `reason`, `updatedOn`, `syncedAt` exist — no "snoozed until" or "deferred" concept). This design treats delay/snooze as **session-only, ephemeral state in the companion app** (skip this task for the rest of the current voice session, re-offer it next session) rather than a persisted schema change — avoids a cross-app schema migration for a v1 personal tool. Promoting this to a real persisted field is future scope, not v1.

## Cross-Model Perspective

Independent Claude subagent cold read (Codex not installed on this machine):

1. **Coolest unconsidered version:** a _continuity_ coach — Ollama keeps a rolling memory across sessions (e.g. "you've snoozed 'call best friend' three Mondays running — want me to just move it to weekends?"), renegotiating the task's recurrence itself instead of only executing done/delay/snooze on a fixed cadence. Small to add later: a rolling summary written into storage, fed into the system prompt.
2. **What reveals the real excitement:** the user's own words — "runs continuously in a tab/widget while the user works, listens for 'done'/'next' rather than being a discrete request/response session." The appeal is ambient presence, not voice-as-input-method; push-to-talk would deliver 90% of the hands-free value with none of the false-positive-listening headaches, and the user explicitly didn't want that tradeoff.
3. **Existing OSS coverage:** "Ollama + Web Speech STT + Kokoro TTS in the browser" demo repos already combine these three pieces (mic capture, streaming chat, TTS playback queueing, basic barge-in) — roughly 40-50% of the plumbing. Not covered anywhere: mapping spoken intent onto What Now's specific task schema, missing-field detection/follow-up, listening cadence tuned to task review (vs. generic chat), or cross-session memory.
4. **Weekend build order suggested (not adopted — user chose to keep full voice from day 1):** validate the dialogue/intent logic over text first, then bolt on voice. The user explicitly declined this de-risking step and chose to build voice + always-on listening together from the start — noted as a deliberate risk acceptance, not an oversight.
5. **Premise 3 sanity check confirmed:** localhost-from-HTTPS is not blocked by mixed content; `OLLAMA_ORIGINS` is the real and sufficient gate. Chrome's Private Network Access tightening is an emerging risk to document, not a current blocker.

## Approaches Considered

### Approach A: Minimal Coach Loop

A page inside What Now itself: on load, Ollama picks the top active task, speaks it via Kokoro with its reason (asking for one if missing), continuous mic listens for done/delay/another/snooze intents classified by Ollama, loop repeats. No cross-session memory.
Effort: M. Risk: Med (continuous STT + intent accuracy is the main unknown).
Reuses `isTaskActive`, `TaskSchema.reason`, existing task CRUD utils directly by importing them in-process — this direct reuse is only available because the page lives inside What Now's own codebase.

### Approach B: Coach + Rolling Memory

Same as A, plus a small memory record (rolling summary of recent snoozes/delays per task) feeding the Ollama prompt so the coach can suggest rescheduling repeatedly-dodged tasks.
Effort: L. Risk: Med-High (summarization quality and prompt drift are new failure modes).
This is the "whoa" feature identified by the cross-model review, but adds real build/test surface for a first slice.

### Approach C: Coach as a Standalone Companion App (SELECTED)

A separate small local web app, not merged into the What Now codebase, that talks to What Now's task data via the existing Convex sync deployment (already built, per recent commits) or the JSON export/import format. What Now's core planner code is untouched by this experiment.
Effort: L. Risk: High (two codebases; the companion must reimplement `isTaskActive`-equivalent scheduling logic since it can't import `src/utils/tasks.utils.ts` across a repo boundary — a real, uncosted piece of duplicated logic, not free reuse).
Reuses the Convex sync template (`convex/`) as the live data bridge, and/or the export/import JSON schema for a lighter-weight, sync-free version. Note: code isolation is not data isolation — the companion writes through the same `upsertTask` mutation against the same live Convex deployment the core app reads from, so a buggy companion can still corrupt real task data even though no What Now source code is touched.

## Recommended Approach

User selected **Approach C: Standalone Companion App**, with the repo-location decision refined during /plan-eng-review to a `/coach` subdirectory of `what-now` rather than a fully separate sibling repo (see Architecture Decisions). Rationale volunteered implicitly by the original choice: keep this experimental, always-listening, cloud-touching (via Chrome STT) voice feature isolated from What Now's core local-first planner's _source code_ — a broken or abandoned coach experiment can be rebuilt or discarded without regressing the main app's shipped code. With the `/coach`-subdirectory refinement, this isolation is now a code-organization discipline (a distinct directory with its own build) rather than a separate-repo structural guarantee, and it shares CI/`pnpm check`/PR surface with the core app. This is code isolation, not data isolation either way: the companion still reads/writes live task data through the same Convex deployment, so it must be built to the same data-integrity bar as any other client of that deployment (see Approach C risk note above).

Given the standalone-app framing, the data bridge should default to the **Convex sync deployment** (already built and working per `d2e3a1d` / `71bbdf6` in the git log) rather than file-based import/export, since it gives the companion live read/write access without the user having to manually shuttle JSON files between apps every session.

## Open Questions

- How should the coach avoid false-triggering on unrelated speech given always-on listening was chosen deliberately — is there any lightweight guard (e.g. requiring the transcript to match one of a small set of task-control phrases before acting) planned, or is that left fully to Ollama's intent classification? **Still open** — unaffected by the Pipecat pivot.
- Multi-missing-attribute tasks: does the coach ask about all missing attributes in one turn, or one per turn across multiple exchanges? Unresolved — pick whichever is simpler to prompt-engineer reliably in Ollama; either is acceptable for v1. **Still open** — unaffected by the Pipecat pivot.
- Whether 4 sequential Ollama calls per turn (see Architecture Decisions below) fit the ~2s latency budget is unmeasured — now addressed by a dedicated timing spike as Next Steps step 2, moved earlier rather than deferred.

**Resolved during review:** `convex/tasks.ts`'s existing `getAllTasks`/`upsertTask` mutations are sufficient for the companion to read active tasks and write completions/reason updates — no new Convex functions are needed for the core loop (delay/snooze are handled as ephemeral companion-side state per Premise 7, not a Convex write).

## Architecture Decisions (resolved during /plan-eng-review)

1. **Companion location:** lives in a `/coach` subdirectory of the `what-now` repo (not a separate sibling repo). This is a deliberate deviation from Approach C's "fully isolated" framing — the user chose to trade some of that isolation for easier in-repo schema-sync, accepting that a `/coach` change and a core-app change can now land in the same PR by accident if not careful.
2. **Stale-queue handling:** the companion subscribes **reactively** to the Convex task query (not a one-time snapshot). This directly avoids the class of bug already observed in this codebase (`local-first-hydration-race` learning, confidence 9/10) where async data loading plus interactive writes before hydration completes caused silent data loss.
3. **Voice pipeline framework (Pipecat pivot — supersedes the original hand-rolled plan):** the audio/voice pipeline is built on [Pipecat](https://github.com/pipecat-ai/pipecat) rather than hand-rolled browser JS. [EUREKA, confidence 8/10] Pipecat already provides: native Ollama integration (`OLLamaLLMService`), built-in barge-in/interruption handling via Silero VAD (eliminating the need for a hand-rolled Web Audio energy gate + echo-cancellation coordination), pluggable local STT (faster-whisper) and TTS (Kokoro/Piper) services, and pipeline/turn-taking orchestration. This trades "one more local service to run" (a Python process alongside Ollama) for "far less custom audio/VAD/turn-taking code to write and debug," and as a side effect fully resolves the STT privacy compromise (Premise 4) since faster-whisper runs locally, not in Chrome's cloud.
4. **Barge-in detection:** delegated to Pipecat's built-in Silero VAD-based interruption handling — no custom Web Audio energy gate or manual `echoCancellation` coordination needed; this is a solved problem in the framework, not bespoke code.
5. **STT session lifecycle:** delegated to Pipecat's pipeline management — no custom restart-on-`onend`/backoff logic needed, since Pipecat is not built on Chrome's `SpeechRecognition` API in the first place (it uses faster-whisper, which doesn't have the browser API's silence-triggered auto-stop behavior).
6. **Ollama call structure:** four separate, narrowly-scoped calls per turn (task selection, intent classification, dialogue generation, missing-attribute Q&A), each using Ollama's native JSON-schema `format` parameter (available since Ollama 0.3.0) rather than one combined mega-prompt, issued through Pipecat's `OLLamaLLMService`. Each piece is independently testable and a malformed response from one doesn't corrupt the other three. Tradeoff accepted: four sequential local-model calls may or may not fit the ~2s latency budget — a dedicated timing spike is now Next Steps step 1 (moved earlier, not deferred to the end) precisely because a bad number here would invalidate dialogue pacing and turn-taking built on top of it.
7. **Write validation:** a single shared validate-then-write wrapper sits in front of every `upsertTask` call from the companion (DRY — one place to harden against a malformed Ollama-derived value, rather than duplicating checks at each call site).
8. **Invalid-answer UX:** if an Ollama-derived answer to a missing-attribute question fails validation, the coach re-asks once; if the retry also fails, it tells the user the field is being skipped rather than silently dropping it.
9. **Visibility-loss UX:** on tab backgrounding (or the Pipecat client disconnecting), STT/TTS stop cleanly and a visible "paused" indicator appears; on reconnect, the session resumes with existing in-memory state (the in-session skip list and asked-attributes list survive on the Pipecat server process).
10. **Ollama-unreachable UX:** on session start, if Ollama can't be reached (service not running), show a clear setup-check screen ("Can't reach Ollama at localhost:11434 — check it's running") rather than a blank or broken page. The original `OLLAMA_ORIGINS` CORS concern no longer applies (Premise 3, Pipecat pivot) since Pipecat's server talks to Ollama directly, not the browser.
11. **Convex write-failure UX:** if an `upsertTask` call fails after passing validation (network drop, deployment unreachable), retry once automatically; if the retry also fails, the coach says so out loud ("couldn't save that, try again in a moment") rather than silently losing the completion or answer — the same re-ask-once-then-tell-the-user philosophy as invalid-answer handling (Decision #8), applied consistently to write failures too.

## Success Criteria

- The user can, hands-free, hear the coach announce a task and reason, respond with "done"/"delay"/"another"/"snooze" by voice, and see "done" reflected back in What Now (via Convex sync) without touching mouse or keyboard. "Delay"/"snooze" affect only the current voice session per Premise 7.
- A task missing a `reason` gets asked about by voice and the answer is persisted back to that task via the same Convex mutation the core app uses.
- The core What Now app's source code (planner, local IndexedDB storage, existing sync logic) is unaffected by the companion's existence — it can be deleted or broken without any regression to What Now's shipped code. This does not guarantee data safety: a bug in the companion can still write bad data to the shared Convex deployment, so the companion needs its own input validation before calling `upsertTask`.
- The coach handles an empty task queue (says something like "nothing left today" and stops prompting) and recovers gracefully from a misheard/misclassified utterance (asks for clarification rather than silently acting on a low-confidence guess) — both are baseline behaviors, not stretch goals.
- TTS playback can be interrupted (barge-in) by the user starting to speak, so the coach doesn't talk over them for the full response length every time, and the coach must not pick up and misinterpret its own voice as user speech. Delegated to Pipecat's built-in Silero VAD-based interruption handling (Architecture Decision #4) — validated on real hardware per Next Steps step 5, not assumed to work perfectly out of the box.
- Session state (which tasks have already been asked about this session, which are on the delay/snooze skip list) resets on page load/session restart, consistent with Premise 7's "session-only, ephemeral" framing — not persisted across browser restarts.

## Distribution Plan

Personal tool, not intended for other What Now users initially. Two local processes now required: Ollama (already assumed) and a Pipecat-based Python server (new, per the Pipecat pivot). The browser-side `/coach` page becomes a thin client connecting to the local Pipecat server rather than doing all the work in-browser. If the `/coach` feature is documented for other users later, a section would be added to What Now's own README covering Ollama setup, the Pipecat server's local install/run steps, and Convex deployment URL wiring, mirroring the pattern already used for cross-device sync.

## Measured Results (T1/T2 spike, 2026-08-06)

Ran on the actual target machine: RTX 4070 SUPER (12GB VRAM), Ollama already running.

- **Model choice matters more than call count.** The machine's only pre-pulled model, `glm-4.7-flash:q4_K_M` (29.9B params, ~26GB), doesn't fit in 12GB VRAM — only 10.4GB of it loads, the rest spills to CPU. Result: 83s cold, **13.5s warm** for a single call. Four sequential calls at that rate would be roughly a minute per turn — the ~2s ambient-feel budget was never going to survive this model, independent of the 4-call architecture decision.
- **Switched to `llama3.2` (3.2B, ~2GB)** — fits fully in VRAM. Warm latency: **as low as 130ms per call** once tuned (see next point). Four sequential calls at that rate is well under half a second total, comfortably inside the ~2s budget.
- **Gotcha found: default context window silently forces CPU offload.** `llama3.2`'s default `num_ctx` (64k tokens) reserves enough VRAM for KV cache that the model doesn't fully fit alongside it, causing intermittent 5-6s latency even on a model that should be fast. Explicitly capping `num_ctx: 2048` (plenty for these short coach prompts) fixed it — consistent ~130-400ms/call after that.
- **Gotcha found: `num_ctx` must go through `extra_body`, not `extra` directly.** `OllamaLLMSettings(extra={"num_ctx": 2048})` merges flat into the OpenAI SDK call's kwargs (`OLLamaLLMService` talks to Ollama via its OpenAI-compatible endpoint), and `num_ctx` isn't a real OpenAI API parameter — the SDK rejects it (`AsyncCompletions.create() got an unexpected keyword argument 'num_ctx'`), which surfaced as a silent `ErrorFrame` deep in the pipeline rather than a visible startup error. Fix: `OllamaLLMSettings(extra={"extra_body": {"options": {"num_ctx": 2048}}})` — `extra_body` is openai-python's standard escape hatch for provider-specific fields, and Ollama's OpenAI-compat layer reads Ollama options from `extra_body["options"]`.
- **Gotcha found: `vad_analyzer` is not a real field on `LocalAudioTransportParams` in Pipecat 1.7.0.** Passing it there (a pattern from older docs/examples) is silently accepted by pydantic and does nothing — confirmed via `LocalAudioTransportParams.model_fields` not listing it. Result: raw audio flowed through the pipeline correctly (confirmed via an explicit frame counter), but nothing ever segmented it into an utterance, so STT never finalized anything and the LLM/TTS never fired — this was the actual root cause of "no reaction to my voice" across several debugging rounds. Fix: VAD must be its own explicit `VADProcessor(vad_analyzer=SileroVADAnalyzer())` pipeline stage, inserted between the transport and STT.
- **Gotcha found: `faster-whisper`'s `device="auto"` (the default) silently fails on this machine.** It detects the GPU and attempts CUDA via ctranslate2, which needs `libcublas.so.12` — not installed here. The failure surfaces as a per-utterance `ErrorFrame` (`Library libcublas.so.12 is not found or cannot be loaded`), not a startup error, so every utterance just vanished with no transcription and no indication why. Fix: force `device="cpu"` explicitly; the "base" Whisper model is fast enough on CPU for short utterances.
- **Gotcha found: `LocalAudioTransportParams`'s implicit "default" PyAudio device does not reliably match the OS's actual default audio device.** On this machine, PyAudio's `get_default_input_device_info()` resolved to a device that captured silence with no error, while `pw-record --target <pipewire-source-id>` (bypassing PyAudio) captured real audio from the same physical mic correctly. Fix: explicitly look up and pass the PyAudio device index for the `"pipewire"` ALSA-compatible meta-device by name (not by hardcoded index, since indices shift across runs) as both `input_device_index` and `output_device_index`.
- **Gotcha found: `KokoroTTSService` requires an explicit `voice` — no default.** `KokoroTTSService()` with no voice constructs fine but throws `"Kokoro TTS voice must be specified"` as a runtime `ErrorFrame` only once TTS actually runs, not at startup. Fix: `KokoroTTSService(settings=KokoroTTSService.Settings(voice="af_heart"))` — full voice list (56 options across languages/genders) via `kokoro_onnx.Kokoro.get_voices()`.
- **Conclusion for Architecture Decision #6:** the 4-call-per-turn structure is validated as latency-safe, but _only_ with a small model (≤4B-ish) and an explicitly capped `num_ctx` via `extra_body`. This is now a hard requirement for Next Steps step 3's model choice, not a nice-to-have — a larger/more capable model would need to be evaluated against this same VRAM/num_ctx math before being substituted in.
- **Gotcha found: Pipecat's built-in Silero VAD barge-in does NOT prevent the coach hearing itself, on this hardware, even through headphones.** Next Steps step 5 explicitly called for validating this rather than trusting it — it failed on both attempts. First attempt (speaker output): VAD retriggered constantly on speaker-to-mic bleed, causing a runaway self-interrupt loop. Second attempt: routed TTS output to headphones instead of speakers (input mic unchanged) — still looped, confirmed via Whisper transcribing a fragment of the coach's own recent sentence ("Your task for to", matching "Your task for today is to..."), meaning even headphone audio leaked audibly into the room and reached the webcam mic. A parallel attempt to fix this properly via PipeWire's WebRTC echo-cancel module (`libpipewire-module-echo-cancel`, `aec.method=webrtc`) loaded successfully but produced a silent virtual mic device (zero signal, confirmed via raw RMS capture) — not reliable enough to use within spike-scope debugging time.
- **Fix adopted: hard software mute gate, not acoustic isolation.** A `MuteWhileBotSpeaking` FrameProcessor drops all `InputAudioRawFrame`s while `BotStartedSpeakingFrame`...`BotStoppedSpeakingFrame` is active, plus a 0.5s cooldown after the bot stops (for output tail/room decay). This sidesteps the echo problem entirely at the cost of barge-in: **the user cannot interrupt the coach mid-sentence** — confirmed by the user as the first real UX friction point ("not super smooth... also I can't interrupt the agent"). This is an explicit, accepted tradeoff for the spike, not an oversight; real barge-in support would need working AEC or a headset with a boom mic positioned away from the ear speakers (physically minimal leak path) — deferred, not solved.
- **T1 spike pipeline verified end-to-end, including live voice interaction — SUCCESS.** All six gotchas above were found and fixed through live debugging with the user: VAD correctly detects real speech, Whisper transcribes accurately, Ollama responds without error, Kokoro speaks audibly, and with the mute gate in place the coach completes a full turn without self-interrupting. User's own assessment: "worked nice, its not super smooth interaction tough, also I cant interupt the agent" — the core loop works; interaction smoothness and interruptibility are the next things to improve, not blockers to the concept.
- **Per-step timing instrumentation added and measured across 3 real exchanges** (`coach/server/timing.py`, a non-intrusive `BaseObserver` that watches every frame with zero pipeline wiring changes). Frame-based events dedupe correctly by canonicalizing Pipecat's broadcast-pair `id`/`broadcast_sibling_id` into one logical event. Auto-stops itself after N exchanges (`stop_after_turns` on `TimingLog`, cancels the `PipelineTask` from inside the running pipeline) rather than relying on Ctrl+C — live testing showed the graceful-shutdown path (both Pipecat's own SIGINT handler and a `finally` block) intermittently never completed after an interrupt, cause not fully root-caused; an `atexit`-registered idempotent `print_summary()` is a second safety net regardless.
  - **Longest steps across the 3 measured turns:** audio playback dominates every turn (3.7-4.9s, proportional to response length — not a bottleneck, it's inherent to speaking the response aloud), turn 1 pays a real cold-start tax (2.71s gap before the agent starts + 2.02s time-to-first-token, matching the cold-vs-warm Ollama latency measured earlier via curl), turns 2-3 don't pay it once the model is warm (0.003s and 0.14s respectively). Listening and STT themselves are fast (0.32-1.15s) — not where time goes.
  - **Unexplained finding:** turn 3 had a 1.86s "STT done → agent query start" gap despite being warm, which turn 2 didn't have (0.003s). Possibly growing conversation context or smart-turn end-of-turn analysis taking longer as history accumulates — not investigated further, flagged for whoever picks up T2's latency work next.
- **French mode tried and measured — quality rejected by the user ("speaks french really badly and like a robot").** System prompt switched to French (translating the English-authored task on the fly), Kokoro TTS switched to its only French voice (`ff_siwis`), Whisper STT switched to expect French input. Required two more fixes to even get audio out: (1) `espeak-ng`'s actual binary wasn't installed (only its data/library packages were) — Kokoro's phonemizer needs it for any non-English language; (2) Pipecat's own `language_to_kokoro_language()` maps `Language.FR` to the bare code `"fr"`, but this machine's espeak-ng only recognizes region-qualified codes (`"fr-fr"`, `"fr-be"`, `"fr-ch"`) — `"fr"` alone raises `RuntimeError: language "fr" is not supported by the espeak backend`. Fixed by passing the raw string `"fr-fr"` directly to `KokoroTTSService.Settings(language=...)`, which bypasses that broken mapping function entirely (confirmed via source read: the actual synthesis call passes `self._settings.language` straight through to `kokoro_onnx`, never calling the mapping function). Even after both fixes, the French voice's quality itself was rejected on subjective grounds — Kokoro's single French voice model is simply not as polished as its English ones.
  - **French measured performance was also markedly worse, not just voice quality:** TTS synthesis 2.5-3.7s per turn (vs. 0.2-1.7s in English), audio playback 7.6-12.0s per turn (vs. 3.7-4.9s in English) — both roughly 2-3x slower than the English baseline, though some of this may be French responses simply being longer/more verbose rather than a pure per-character synthesis slowdown; not isolated further.
  - **Decision: pivot away from Pipecat/Kokoro for voice quality, toward an in-browser experiment.** Rather than chase a better local French TTS voice (Kokoro has only one, and swapping TTS engines entirely is a bigger change), the user chose to build a parallel experiment: a new page inside the `what-now` web app itself, using the browser's native Web Speech API (STT + TTS) and Chrome's built-in on-device AI (the Prompt API / Gemini Nano) instead of Ollama+Whisper+Kokoro+Pipecat. English first, same timing instrumentation, for a direct side-by-side comparison against the numbers above. This does not retire the Pipecat spike — both remain live options pending this comparison.

## Browser Experiment (`/coach-browser`, 2026-08-06) — Web Speech API + Chrome's on-device Prompt API

Built as `src/pages/page-coach-browser.tsx` in the `what-now` web app itself (not `coach/`) — Web Speech API (`SpeechRecognition` + `speechSynthesis`) for STT/TTS, Chrome's `LanguageModel` (Gemini Nano, on-device) for the LLM. Same task, system prompt, and 3-exchange auto-stop as the Pipecat spike's English baseline, same timing event taxonomy (`src/utils/browser-coach-timing.utils.ts` mirrors `coach/server/timing.py`) for a direct comparison. No server, no Ollama, no Python — everything runs in the browser tab.

**Real gotchas found and fixed, all via live testing:**

- **`LanguageModel.create()` requires a real user gesture** when the model needs downloading — a JS-triggered click (e.g. from an automated test) doesn't count, only a genuine click event does. Confirmed via browser automation: the exact same code failed with `NotAllowedError: Requires a user gesture` when triggered programmatically, and succeeded with a real click.
- **Only one "fresh user activation" is available per click, and two APIs competed for it.** `LanguageModel.create()`'s download (can take a while) and the microphone permission prompt both need that same activation window. Requesting mic permission _after_ the model finishes downloading meant the activation had expired by then — Chrome silently returned `not-allowed` instead of prompting, even on a real click. Fixed by calling `navigator.mediaDevices.getUserMedia({audio:true})` first, immediately on click, before any model/download work (`primeMicrophonePermission()`) — the permission grant itself persists for the page's lifetime once obtained, so front-loading it sidesteps the scarce-activation problem entirely.
- **Chrome's own audio device list can go stale after the OS audio server restarts.** After the earlier PipeWire restart (from the AEC detour on the Pipecat side), Chrome kept reporting `NotFoundError: Requested device not found` from `getUserMedia`, even though PipeWire itself correctly showed the mic as the default source and OS/site permissions were both granted. A full Chrome restart (not just a tab reload) forced a clean device re-enumeration and fixed it.
- **Automated browser testing (this session's own browser-automation tooling) cannot exercise the mic-dependent path.** Verified via direct JS: `enumerateDevices()` in the automated tab showed zero `audioinput` devices (only the webcam's `videoinput`), and `getUserMedia` failed with the same `NotFoundError` — the automated tab is isolated from real audio hardware, same class of limitation as the Python spike's sandboxed testing environment. Everything _not_ mic-dependent (model download, session creation, timing instrumentation) was verified working via real clicks in the automated browser before handing off the live mic test to the user.

**First measurement run had a real methodology bug — user caught it, corrected before drawing conclusions.** The initial "listening" instrumentation recorded `listening_start` the instant the page began _waiting_ for speech (before `recognition.start()`), not when the user actually started talking — silently including reaction/thinking time. Pipecat's `listening_start` is VAD-driven and only fires once real speech is detected, so the two numbers weren't measuring the same thing; this made the browser's "listening" step look 8-10x slower than Pipecat's when the gap was partly a measurement artifact. Fixed by switching to `SpeechRecognition`'s own `speechstart`/`speechend` events (the API's real detected-speech boundaries) instead of the recognition-start/result lifecycle — see `listenOnce()` in `src/utils/coach-browser-session.utils.ts`.

The first run's TTS numbers were also initially mischaracterized as "slower than Kokoro" without checking _why_. Added a diagnostic log (response character count + which voice/`localService` flag actually spoke it) before re-measuring.

**Measured results, 3 real exchanges, English, after both fixes:**

| Step                                                                 | Browser (Web Speech + Gemini Nano) | Pipecat (Ollama + Whisper + Kokoro) |
| -------------------------------------------------------------------- | ---------------------------------- | ----------------------------------- |
| Listening (real speech duration, speechstart→speechend)              | 0.80-1.30s                         | 0.3-0.5s                            |
| Agent time-to-first-token, turn 1 (cold)                             | 0.27s                              | 2.02s                               |
| Agent time-to-first-token, turns 2-3 (warm)                          | 0.40-0.43s                         | 0.13-0.14s                          |
| Agent full response                                                  | 0.40-1.72s                         | 1.06-1.61s                          |
| TTS + playback (223 / 53 / 104 chars spoken)                         | 12.18s / 3.91s / 6.63s             | 3.68-4.93s                          |
| Total per-turn cycle (listening_start to next listening_start / end) | 16.06s / 7.55s / 8.51s             | 6.7-13.0s (turn 1) / 6.7s (turn 2)  |

**Corrected interpretation:**

- **Listening duration is now genuinely comparable** (0.8-1.3s vs Pipecat's 0.3-0.5s) — still somewhat slower, but nowhere near the original 8-10x gap, which was mostly the reaction-time bug.
- **TTS duration checks out as real speech, not lag.** Character-rate math: 223 chars / 12.18s = 18.3 chars/sec (turn 1), 53 chars / 3.91s = 13.6 chars/sec (turn 2), 104 chars / 6.63s = 15.7 chars/sec (turn 3) — all within or above the ~12-15 chars/sec natural human speech rate (150 wpm). The "slow" TTS wasn't a performance problem; it was correctly measuring a longer, natural-paced spoken response. Turn 1's larger total (16.06s) traces directly to Gemini Nano generating a longer response (223 chars) that turn, not a systemic slowdown — turns 2-3 (7.55s, 8.51s) land close to or better than Pipecat's ~6.7-13.0s range.
- **New finding, not previously surfaced: the default voice is `"Google US English"` with `localService: false`** — a network-dependent cloud voice, not an on-device/offline one. This is almost certainly why voice _quality_ was judged "way better" than Kokoro (it's a production-grade Google TTS voice) — but it also means this experiment isn't actually the fully local/offline solution its framing implied; it depends on reaching Google's TTS servers. Worth a real decision later: is losing full offline capability an acceptable tradeoff for voice quality this much better, or does a future iteration need to force a `localService: true` voice for a fair apples-to-apples (and privacy-preserving) comparison?
- **Gemini Nano still shows no meaningful cold-start tax** (0.27s turn 1 vs 0.40-0.43s turns 2-3 — if anything turn 1 was _faster_), unchanged from the first run and still a real advantage over Ollama's 2.02s cold-start penalty.
- **Net, corrected: the browser path is now roughly comparable to Pipecat overall**, not 25-50% slower as first (wrongly) reported — the earlier conclusion was an artifact of the listening-measurement bug plus an unexamined assumption that longer TTS meant "slow" rather than "genuinely more content, spoken naturally."
